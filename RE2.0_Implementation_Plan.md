# RE 2.0 Masterplan Engine — Implementation Plan

## Root causes

Every symptom in the audit traces back to one of three things. Fix order matters because #2 and #3 downstream depend on #1.

1. **Data loss** — `project_features` (client form input) gets dropped or partially extracted before it ever reaches Claude. The client's actual choices never influence generation.
2. **Repair-order bug** — `resolve_layout()` runs *before* `BoundaryEngine`/`CollisionEngine` validation instead of after. Validation finds fresh violations against the already-"fixed" layout, and nothing repairs those.
3. **LLM-freehand geometry** — towers, roads, and paths are raw `x_pct`/`y_pct`/bezier coordinates generated by the LLM instead of deterministic math, so precision and consistency vary run to run.

Rendering/visual gaps are downstream of these — polishing `Canvas2D.jsx` before the layout itself is structurally correct will make bugs look prettier, not disappear.

## Phase 0 — Immediate patches

- [ ] **Reorder the pipeline.** Change call order to `LLM → BoundaryEngine/CollisionEngine → resolve_layout() → return`, or add a second `resolve_layout()` pass after validation. This is the single highest-leverage bug — repair currently runs, then validation finds new violations against the repaired layout, and nobody fixes those.

- [ ] **Trace the full data path** from `ProjectRequirementsForm.jsx` through to the final prompt string sent to Claude in `/ai/suggest`. Identify the exact step, if any, where user input stops affecting output.
- [ ] **Replace manual field-by-field `user_reqs_str` extraction** with passing the full `project_features` dict (or at minimum add the missing fields: clubhouse, unit_specifications, sustainability). Stops the prompt from going stale every time the form schema grows.

**Outcome:** layouts stop violating their own constraints, and the client's actual form inputs stop being silently discarded. This alone may close most of the "ignores what I asked for" and "looks broken" complaints.

## Phase 1 — Guardrails around generation
**Effort: low–medium · Impact: high · Target: 1–2 weeks**

- [ ] **Bounded retry loop in `/ai/suggest`.** When `report['grade']` is C or F, re-prompt Claude with the specific `conflicts`/`boundary_violations` list instead of returning a known-bad layout. 2–3 attempts.
- [ ] **Procedural fallback on retry exhaustion.** If retries still fail, fall back to a deterministic procedural layout rather than shipping a broken one to the frontend.
- [ ] **Model version audit.** Confirm no other place besides `ai.py` hardcodes `ANTHROPIC_MODEL`, and move off `claude-3-5-sonnet-20240620` to a current model. Check for stray fallback strings too.

**Outcome:** the system has a safety net — bad layouts get a second/third chance instead of shipping straight to the user.

## Phase 2 — Procedural geometry engine
**Effort: high · Impact: very high · Target: 2–4 weeks (decision point below)**

The architectural fix: split *what* (content, an LLM choice) from *where* (geometry, a math problem).

| Claude decides (content) | Code decides (geometry) |
|---|---|
| Which amenities to include | Tower ring positions on an ellipse |
| Unit mix & tower footprint style | Loop-road path |
| Land-use percentages | Inner jogging track |
| Labels & naming | Setback & spacing math |

- [ ] Check `utils/planningEngine.js` / `geoUtils.js` first for existing deterministic placement utilities before writing new ones.
- [ ] Refactor `USER_PROMPT_TEMPLATE` so Claude no longer generates raw coordinates for towers/roads/paths — only the content decisions above.
- [ ] Build deterministic placement functions for tower rings, loop-road path generation, and jogging-track offset from the loop road.

**Decision point:** if Phase 0–1 fixes get output close enough to the reference image, defer this. If towers still drift, overlap, or look inconsistent between runs, this is non-negotiable.

## Phase 3 — Rendering & visual fidelity
**Effort: medium · Impact: medium · Target: 2–3 weeks (after layout is trustworthy)**

| Area | Current gap | Fix |
|---|---|---|
| Street-grid basemap | Unclear if `Canvas2D.jsx`/`MapSelector.jsx` renders a real basemap under generated elements, or floats them in isolation | Wire up basemap rendering in the editor view if missing |
| Roads | Missing lane markings, medians | Add stroke-based lane/median styling in `Canvas2D.jsx` |
| Tree clusters | Flat/generic vs. reference's organic clustering | Cluster placement + varied icon/texture rendering |
| Amenity icons & towers | Reference uses numbered tower markers, concentric jogging path, clustered central amenities | Icon set + numbering + concentric path rendering, built on Phase 2's geometry output |

**Visual roadmap ideas beyond closing the reference-image gap:**
- Style presets on one underlying layout — engineering/CAD, marketing brochure, satellite/map-like, luxury render, isometric 3D. Decouples "is the layout correct" from "does it look good."
- Layer toggles in the editor (roads / greenery / amenities / setback zones / grid) so a user or developer can isolate what they're looking at.
- Diff view: show before/after when `resolve_layout()` or the retry loop repairs a layout, so fixes are visually confirmable instead of trusting the grade number alone.

## Phase 4 — Architecture evolution
**Effort: high · Impact: medium–high · Target: ongoing, longer horizon**

- [ ] **Separate planning from rendering** as distinct modules/services. Not just a styling change — makes the renderer stateless and swappable across the Phase 3 style presets.
- [ ] **True constraint solver ahead of generation** (rather than generate-then-repair). Define setbacks/spacing as hard constraints an optimizer respects from the start, cutting down how often repair/retry is even needed.
- [ ] **Multi-agent split** (only once Phase 2's single-model content/geometry split hits its limits): `Planner → Road agent → Landscape agent → Amenity agent → Validator → Renderer`. Each agent has a focused task, reducing hallucinations and isolating failures. This is a scaling move, not a bug fix — don't start here.
